El problema

Llegar a una base de datos privada suele pasar por un bastion SSH

Puerto 22 abierto

Un servidor expuesto a internet es superficie de ataque permanente.

Claves compartidas

Claves SSH repartidas por el equipo, difíciles de rotar y de revocar.

Poca trazabilidad

¿Quién entró, cuándo y con qué permisos? Un problema para auditorías.

La solución

AWS SSM Session Manager, reducido a un solo comando

$ ssmgate db --env dev

login SSO → rol → túnel SSM → token IAM 15 min → psql

Conexión saliente desde la instancia: cero puertos de entrada. Cada sesión ligada a tu identidad SSO y registrada en AWS.

Qué hace

Tres comandos principales

ssmgate shell bastion

Shell interactiva en cualquier instancia gestionada por SSM, con un rol SSO por host

ssmgate db

Túnel a la base de datos privada + token IAM de 15 minutos + psql con SSL

ssmgate tunnel

Túnel abierto para DBeaver o TablePlus; el token se copia al portapapeles

Y además: envs, config init · validate, doctor y el modo --demo. Todos exigen --env explícito.

Genérico

Tu infraestructura vive en un YAML, no en el código

  • Entornos, cuentas, hosts, roles y BBDD
  • SSO integrado o perfil de la AWS CLI
  • Validación estricta con todos los errores a la vez
  • confirm: true protege producción

environments:
  prod:
    region: us-east-1
    account_id: "222222222222"
    confirm: true
    hosts:
      bastion:
        instance_id: i-0aaa…
        role: BastionSessionOperator
    db:
      endpoint: prod-db.…rds.amazonaws.com
      name: appdb
      local_port: 55433
      via: bastion
      role: RDSOperator

Funcionalidades

Pensado para el día a día de un equipo

Rol por host

Mínimo privilegio: cada servidor exige su propio rol SSO.

Prod protegido

Hay que escribir el nombre del entorno antes de actuar.

Túneles en paralelo

Un puerto local por entorno: dev y prod a la vez.

Sesión reutilizable

Caché SSO compatible con la AWS CLI.

Multiplataforma

Windows, Linux, macOS y WSL; amd64 y arm64.
